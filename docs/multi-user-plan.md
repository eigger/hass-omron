# 1인용 기기 멀티유저 계획 (#301)

상태: 구현됨(베타 사전 릴리스 전, 실기기 미검증). 구현 중 달라진 점은 맨 아래 "구현 메모"에 있다. 근거: 이슈 #301, 자매 저장소 hass-atflee의 사용자 구조, 코드 대조 검토. 인용한 코드 위치는 검토 시점 기준이며 구현 때 다시 확인한다.

## 목표

- 사용자를 등록하지 않으면 지금과 완전히 같다.
- 사용자를 등록하면 새 측정마다 배정 방식에 따라 사용자를 정해 그 사용자의 센서를 갱신한다.
- 대상은 기기가 사람을 구분하지 못하는 1인용 기기(`num_users == 1`): 체중계 HN-300T2(`is_weight_only_scale`)와 사용자 슬롯이 1개인 혈압계(예: HEM-7600T). 슬롯이 여러 개인 혈압계의 기존 슬롯 방식(`user`/`user_alias`)은 건드리지 않는다. 서브엔트리는 `num_users == 1`일 때만 제공한다.
- 비목표: Active user 셀렉트와 `person` 존재 필터(폴링으로 저장 기록을 나중에 읽는 구조라 읽는 시점의 선택·존재 상태가 측정 시점과 일치하지 않음), HBF 프로파일, 사후 재배정, 새 기록 순번 방식 추가.

## 출시 조건

아래 "사용자 기반"과 "배정 방식"을 모두 구현·검증한 뒤에만 정식 출시한다. 일부만 구현한 상태로는 정식 릴리스하지 않는다. 그 전에 베타 사전 릴리스로 실기기 검증을 받는다. 구현은 기능 브랜치에서 한다. 출시 범위에서 제외하는 것은 "이후" 항목뿐이다.

## 입력 모드

배정기는 기기가 지금 내놓는 경로를 그대로 따른다. 새 순번 방식을 만들지 않는다.

| 기기 상태 | 입력 | 비고 |
|---|---|---|
| 저장 기록 동기화 켜짐 (순번 카운터가 있는 슬롯 1개 혈압계, HEM-7530T, 6161T, 7136T, 6231T(변형 6231T_Z 포함), 7153JT, 7150T, 7157T, 7151T, 7142T2) | `pending_history["events"]` 여러 건. 이벤트는 측정 시각 순으로 정렬돼 있으므로 배정기가 순번으로 다시 정렬한다 | 완료된 동기화에서만 최신 기록이 포함된다. 첫 동기화, 리베이스, 읽기 실패, 읽기 한도(`HISTORY_MAX_READS`) 초과분, 비정상 기록은 이벤트에 없거나 다음 폴링으로 넘어간다 |
| 동기화 꺼짐 또는 미지원 (HEM-7600T, HN-300T2: 동기화 미지원이라 옵션이 아예 없음) | 폴링당 최신 1건(`last_record`) | 폴링 사이에 여러 번 재면 앞의 측정은 배정되지 않는다 |

- 모드는 기기 단위로 정해지며, 동기화 옵션이 켜져 있으면 이벤트만, 아니면 최신 1건만 처리한다. 한 폴링에서 두 입력을 함께 처리하지 않아 같은 기록의 이중 배정을 막는다.
- 동기화 미지원 기기에 나중에 순번 방식이 생기면 코드 변경 없이 윗줄로 올라간다.
- 동기화를 켜고 끌 때(모드 전환) 같은 기록이 다시 배정되지 않도록, 기록 지문은 두 모드 모두에서 갱신한다. 동기화 모드에서도 지문은 읽기에 성공한 폴링의 `last_record`(EEPROM)로 갱신한다. 읽기 실패로 `last_record`가 `None`이면 지문을 바꾸지 않고 배정도 하지 않는다.
- Store에 지문이 없는 상태의 폴링은 기준선만 잡는다. 지문만 저장하고 배정하지 않아, 기기에 남아 있던 오래된 기록이 등록 직후 배정되지 않는다(동기화 모드의 첫 동기화와 같은 동작). 따라서 등록 후 첫 측정은 배정되지 않을 수 있으며 문서에 고지한다.

## 1. 사용자 기반 (배정 방식과 무관한 공통 부분)

- 사용자 = 기기 config entry의 서브엔트리. 서브 디바이스 1개와 사용자별 센서를 가진다. 입력 화면은 배정 방식에 따라 항목이 달라지는 구조로 만든다.
  - 체중계: Weight, BMI
  - 혈압계: Systolic, Diastolic, Pulse, Measured At, 파생 지표(맥압, 추정 평균동맥압, 혈압 분류, 쇼크 지수, 심부담도), 이진 플래그(불규칙 맥박, 신체 움직임, 커프 착용, 자세 불량). 속성: `assignment`, `irregular_pulse`, `body_movement`.
- 기존 기기 엔티티는 그대로 둔다. 사용자 센서와 중복되지만 디바이스와 이름이 다르다.
- 배정기는 교체 가능한 전략이며 기기당 하나만 쓴다(사용자별로 다르게 쓰지 않는다).
- 미배정이면 `omron_unassigned_measurement` 이벤트(측정값, `measured_at`, `reason`, `candidates`)를 내고 누구에게도 기록하지 않는다. 사용자 센서에는 `assignment` 속성(`matched`, `nearest`, `rule`)을 둔다.
- 기록은 동기화가 켜져 있으면 이벤트를 순번 순으로(한 바퀴 돈 링 버퍼는 순번 비교에 주의), 아니면 최신 1건으로 처리한다. 기기 시계는 틀릴 수 있고 `datetime`이 `None`일 수 있다.
- 배정기는 기기 종류에 맞는 전략만 고를 수 있다: 체중계는 체중 기반 또는 사용자 지정 규칙, 슬롯 1개 혈압계는 사용자 지정 규칙만. 선택은 config entry 옵션에 저장하고, 바꾸면 사용자별 상태(최근 배정 체중 등)를 초기화한다.
- 이벤트의 `reason` 값: `ambiguous`, `no_match`, `no_time`, `out_of_range`(체중 기반에서 가장 가까운 사용자도 폴백 한도를 넘음). `candidates`는 `user_id`, `name`, 기준 값, 차이(체중 기반) 또는 통과/탈락한 규칙(규칙 기반)이다.

### 선행 과제 (코드 대조 결과)

1. **같은 기록을 두 번 배정하지 않기.** `last_readout_at`은 같은 기록을 다시 읽어도 매 폴링마다 갱신되어 새 기록 판별에 쓸 수 없다(`parser.py:1271-1281`). `_last_record_signature`는 메모리뿐이며 저장만 되고 비교에 쓰이지 않는다(`parser.py:114`, `:199`, `:1258-1260`). 그래서 중복 제거가 없다.
   - 조치: 기록 지문(측정 시각 + 값)을 Store에 저장하고 바뀐 경우만 새 기록으로 본다. 동기화 켜짐 모드에서는 마지막 처리 순번을 함께 저장한다.
   - 한계: 시각이 `None`이면 값만으로 키를 만든다. 같은 값이 연속되면 새 기록을 놓칠 수 있다. 시각이 필요한 규칙은 `no_time`으로 미배정한다.
2. **훅이 원본 최신 기록을 얻을 수 없다.** `record`는 읽기 함수 안의 지역 변수이고 `_last_record_signature`는 비공개다. `SensorUpdate`에는 체중계의 체중과 측정 타임스탬프(타임스탬프 발행: `parser.py:650-666`), 혈압계의 sys/dia/bpm이 가지만, 기기 시각(naive)과 기록의 출처(EEPROM 또는 BLS)는 없다.
   - 조치: `self.last_record`를 노출한다. `parser.py:1140` 직후의 EEPROM 기록을 이벤트와 같은 모양(`_history_event`, `parser.py:1026-1062`: `device_time`, `measured_at`, 값, `sequence=None`)으로 저장하고, 읽기 시작 시 초기화한다(`parser.py:1399-1401`).
3. **혈압계의 라이브 BLS 값.** 단일 사용자 경로는 EEPROM 값을 실시간 BLS 기록으로 대체할 수 있다(`parser.py:1171-1206`). `merged = dict(record or {})`(`:1197`)는 `:1140`의 EEPROM 딕셔너리를 건드리지 않으므로, 위 `last_record`가 EEPROM 쪽을 잡으면 배정은 EEPROM 기록으로만 할 수 있다.
   - 알려진 결과: 메인 기기 센서는 BLS 값을, 사용자 센서는 EEPROM 값을 보일 수 있다. 문서에 적는다.
4. **리베이스를 훅이 알 수 없다.** `rebased`(`driver.py:750`)는 `pending_history`로 복사되지 않는다(`parser.py:1024`). 마지막 순번을 리셋하려면 `pending_history`에 `rebased`를 추가해야 한다. 형태는 `rebased: {user: bool}`(슬롯 1개 기기는 user=1)로 한다.

### 구현 설계

- 후크 위치: `__init__.py`의 `async_poll_data`, `history_lock` 블록 안(`:624-632`), `if not runtime.unloading` 안쪽. `async_publish_history`가 지우기 전에 위 표의 입력을 소비한다. 파서는 HA 비의존을 유지한다.
- 동기화가 켜진 경우 첫 동기화는 기준선만 잡고 이벤트를 내지 않으며(`driver.py:723-733`), `lost` 기록이 있을 수 있다(`parser.py:971-977`). 배정기는 둘 다 견뎌야 한다. 카운터가 되돌아가면(`driver.py:738-752`) 선행 과제 4번의 `rebased`로 마지막 순번을 리셋한다. 동기화를 껐다 켜면 위치가 지워져(`history.py:84-85`) `rebased` 없이 첫 동기화로 들어오므로, 최신 1건 모드로 처리하는 동안에는 마지막 순번을 지운다. 순번 비교는 래핑을 고려한다.
- 저장: 새 Store `omron.users_{entry_id}`에 사용자별 상태(전략이 필요로 하는 값, 예: 최근 배정 체중 N건), 마지막 기록 지문, 마지막 순번을 한 번에 저장한다(`history.py:133-145` 방식). 학습한 값과 마지막 처리 위치는 설정 데이터가 아니라 별도 상태 파일에 둔다는 뜻이다. 선택 이유:
  - 엔트리/서브엔트리 데이터에 쓰면 엔트리가 리로드되어 측정마다 통합이 재시작된다(폴링 도중 끊김).
  - `RestoreEntity`는 센서가 비활성이면 복원 데이터가 없고, 값과 위치를 한 번에 저장할 수 없다.
  - Store는 리로드 없이 센서와 무관하게, 한 번의 쓰기로 저장한다.
  - 순서: 배정 → 이벤트 발생 → 저장. 재시작 시 이벤트가 중복될 수 있으므로 보장 수준은 정확히 한 번이 아니라 최소 한 번(at-least-once)이다(`history.py:133`).
  - 제거 시 삭제: `async_remove_entry`(`__init__.py:856-858`)와 서브엔트리 삭제 때.
- 서브엔트리 변경은 엔트리를 다시 로드한다(이 통합의 `update_listener`가 엔트리 변경 시 리로드한다, `__init__.py:853`. 서브엔트리 변경이 리스너를 부르는지는 구현 0번에서 확인). 학습된 값을 서브엔트리 데이터에 쓰면 측정마다 리로드되므로 쓰지 않는다(`history.py:33-34`와 같은 함정).
- 옵션 흐름은 알던 키만 다시 만든다(`config_flow.py:825-857`). 새 옵션(허용 오차 비율 등)은 스키마(`:114-165`)와 `out` 둘 다에 추가해야 저장 때 사라지지 않는다.
- 엔티티 배선(저장소에 선례 없음): 사용자 디바이스에 `identifiers={(DOMAIN, f"{entry_id}_{subentry_id}")}`와 `via_device`, `async_add_entities(..., config_subentry_id=...)`. 기존 엔티티는 `CONNECTION_BLUETOOTH`만 쓴다(`entity.py:36-40`). `unique_id`는 이름이 아니라 `subentry_id` 기반이라 개명 마이그레이션이 없다.
- 사용자 BMI는 서브엔트리의 키를 쓰는 새 엔티티 클래스로 만든다. 기존 `_OmronBmiBase`와 `number.py`의 `_SLOT`, `sensor.py`의 `_BMI_SLOT`, `heights_cm`은 슬롯 1에 고정돼 있어 건드리지 않는다. 체중은 코디네이터의 값이 아니라(마지막으로 잰 사람의 값이다) Store에 있는 그 사용자의 마지막 배정 체중을 쓴다. 기존 BMI(`sensor.py:893-984`)는 참고만 한다. 재시작 뒤 사용자 센서의 마지막 값은 Store에서 복원한다(`RestoreEntity`는 쓰지 않으므로 Store에 사용자별 마지막 값도 함께 저장한다).
- 여러 건이 한 번에 들어오면 기록마다 상태 1건이 "지금" 시각으로 써진다. 사용자 센서에도 `history.py:93-106`과 같은 쓰기 간 대기를 적용하고, `measured_at` 속성을 둔다.

## 2. 배정 방식 (교체 가능한 전략)

모든 전략은 현재 시각(now)에 의존하지 않는 순수 함수이며 `assignment.py`에 둔다. 규칙 기반 전략만 기록의 측정 시각을 입력으로 받는다. 기기마다 등록 시 방식을 하나 정한다.

### 2-1. 체중 기반 (체중계 전용)

구조는 hass-atflee를 따르고, 기준 체중과 허용 오차의 개념은 Etekcity 통합(etekcity_fitness_scale_ble)을 참고만 했다. 상수는 아래 근거로 직접 정했다. 상수는 `const.py`에 모아 두고 코드에 숫자를 흩뿌리지 않는다.

**상수와 근거**

| 상수 | 값 | 근거 |
|---|---|---|
| 기준 체중 창 N | 5건 | 매일 재면 약 한 주. 한두 번의 이상값이 기준을 크게 흔들지 않고, 체중이 서서히 변해도 따라간다 |
| 감쇠 | 배정 순서 기준 반감기 2건 (가중치 1, 0.71, 0.5, 0.35, 0.25) | 최근 값을 더 반영하되 최신 1건이 기준을 좌우하지 않게 한다(최신의 비중 약 35%). 시각이 아니라 순서를 쓰는 이유는 기기 시계를 믿을 수 없기 때문이다 |
| 허용 오차 | 기준 체중의 3%, 하한 1.0 kg, 상한 4.0 kg | 같은 사람의 한 번 측정은 수분, 의복, 측정 시간대, 요일에 따라 흔들린다. 이를 1회 측정 잡음이라 하고, 한 주 안의 체중 변동이 약 0.35%라는 보고보다 개별 측정은 훨씬 크다고 보아 75 kg 성인에서 약 2.3 kg(≈ 잡음의 2배 이상)을 허용한다. 하한은 어린이처럼 체중이 작은 경우에도 1회 잡음을 덮기 위함이고, 상한은 고체중에서 서로 다른 사람이 겹치는 것을 막기 위함이다. 옵션으로 비율을 바꿔도 하한·상한은 그대로 적용한다(비율 허용 범위: 1~5%) |
| 2등과의 최소 차이 | 1.0 kg | 위에서 가정한 1회 측정 잡음 정도. 이보다 가까우면 어느 쪽인지 말할 수 없다 |
| 오차 밖 폴백 한도 | 오차의 2배 이내이고 5.0 kg 이내 | 몇 주에 걸친 체중 변화(감량·증량)는 허용 오차를 넘을 수 있지만, 그 정도(75 kg 기준 약 4.5 kg)를 넘으면 다른 사람이나 손님일 가능성이 더 크다. 약 83 kg 이상에서는 5.0 kg 한도가 먼저 걸려 폴백 폭이 줄어든다(의도) |

근거의 한계: 같은 사람의 하루 단위 체중 변동(표준편차)을 직접 보고한 연구는 찾지 못했다. 찾은 것은 한 주 안의 변동 약 0.35%와 주말·평일 리듬뿐이다([Sydney Uni 보도](https://www.sydney.edu.au/news-opinion/news/2024/07/09/how-often-should-you-really-weigh-yourself-.html), [주말 체중 리듬 연구](https://pubmed.ncbi.nlm.nih.gov/24504358/)). 위 상수는 설계 목표(가족 구성원 분리)에서 정한 가정이며 이 값에서 도출한 것이 아니고, HN-300T2 실사용 데이터로 검증하지 않았다. 그래서 오차 비율은 옵션으로 노출하고, 미배정 이벤트에 기준 체중과 차이를 담아 사용자가 조정할 수 있게 한다.

**분리 가능성(설계 결과)**: 두 사용자의 기준 체중 차이가 `2 × 허용 오차 + 최소 차이`보다 작으면, 한 사람의 측정이 자기 오차 끝에 있을 때 다른 사람과 구분되지 않아 미배정이 나온다. 75 kg 부근에서 이 값은 약 5.5 kg이다. 체중 차이가 약 5.5 kg 이상인 가족은 거의 항상 분리되고, 그보다 가까우면 미배정이 잦아진다. 문서와 설정 화면에 이 기준을 안내한다.

1. 기준 체중: 사용자에게 배정된 최근 5건의 지수 감쇠 평균. 배정 이력이 없으면 예상 체중을 쓴다. 체중 기반에서는 예상 체중이 필수 입력이다. 첫 배정이 생기면 예상 체중을 완전히 대체한다(최신 35%의 비중은 기록이 5건 쌓인 뒤의 값이다).
2. 허용 오차: 위 표대로 기준 체중의 3%를 1.0~4.0 kg로 제한한다. 옵션으로 비율을 조정할 수 있다. 사용자별 표준편차에 맞추는 적응은 하지 않는다.
3. 오차 안의 후보가 있으면 가장 가까운 사용자를 고르되, 후보 전체(오차 밖 포함) 중 2등보다 1.0 kg 이상 가까워야 한다(`matched`). 그렇지 않으면 애매한 경우다. 사용자가 1명이면 이 조건은 없고 오차·폴백 한도만 적용한다.
4. 오차 안에 아무도 없으면 가장 가까운 사용자가 오차의 2배 이내이고 5.0 kg 이내이며 (사용자가 2명 이상이면) 2등보다 1.0 kg 이상 가까울 때만 그 사용자로 배정한다(`nearest`). 서서히 변하는 체중을 놓치지 않기 위함이다.
5. 그 밖의 경우(애매함, 한도를 넘는 손님)는 미배정. 폴백 한도 안의 손님은 구분하지 못하고 배정된다(한계). 미배정은 어떤 사용자의 기준도 바꾸지 않는다.
6. 배정된 체중(`matched`, `nearest`)만 해당 사용자의 최근 5건에 들어간다.
7. 판단에 현재 시각을 쓰지 않는다. 저장된 기록을 나중에 읽는 구조라 읽은 시각이 측정 시각과 다르기 때문이다.

하지 않는 것: 표준편차 기반 적응 허용 오차, 하루 측정 수 제한, `person` 위치 필터, 알림 버튼.

### 2-2. 사용자 지정 규칙: 시간대·값 범위 (슬롯 1개 기기)

#301 작성자의 HEM-7600T(혈압계, 슬롯 1개, 기록에 사람 필드 없음)를 위한 방식이다. 체중과 달리 혈압은 같은 사람 안의 변동이 크고 사람 사이 범위가 겹치므로 값으로 사람을 추정하지 않고, 사용자가 등록할 때 규칙을 직접 정한다.

- 입력(사용자별, 서브엔트리): 시간대(예: 06:00~09:00, 여러 구간 가능), 값 범위(혈압은 수축기/이완기 하한~상한, 체중은 하한~상한). 모두 선택 항목이다.
- 규칙이 하나도 없는 사용자는 모든 기록에 일치한다(등록 시 경고). 사용자가 1명이어도 규칙을 그대로 적용한다.
- 한 사용자의 여러 시간 구간은 OR, 시간대와 값 범위는 AND다. 구간은 시작 포함·끝 제외이고 자정을 넘는 구간(22:00~02:00)을 허용한다.
- 시간대 규칙이 없는 사용자는 기록에 시각이 없어도 `no_time`이 아니라 값 규칙으로 판정한다.
- 판정: 지정한 규칙을 모두 만족하는 사용자를 후보로 삼는다(AND). 후보가 정확히 1명이면 배정(`rule`), 0명이거나 2명 이상이면 미배정(`reason`: `no_match`, `ambiguous`).
- 시각은 `last_record`/이벤트의 `device_time` 벽시계 시각을 쓴다(`measured_at`은 ISO 문자열이거나 `None`이고, 원본 기록의 `datetime`은 naive다). 폴링 시각을 쓰지 않는다. 시각이 없는데 시간대 규칙이 있는 사용자가 후보에 필요하면 미배정(`no_time`)이다(시간대 규칙이 없는 사용자는 위처럼 값 규칙으로 판정). 시계가 틀리면 시간대 규칙은 전부 틀리므로 문서에 적는다. HEM-7600T 프로파일은 시간 동기를 지원한다(`device_catalog.py:408-412`).
- 등록 시 검증: 두 사용자의 시간대가 겹치면 경고한다. 시간대 겹침 경고는 저장을 막지 않는다. 값 범위는 겹쳐도 정상이므로 경고하지 않고 "겹치는 구간은 미배정"이라고 안내한다.
- 신뢰성 고지: 값 범위는 보조 기준이며 오배정 가능성이 있다고 문서에 명시한다. 시간대 규칙은 생활 패턴이 규칙적일 때만 맞는다. 최신 1건 모드에서는 폴링 사이에 여러 번 재면 앞의 측정이 배정되지 않는다.

## 결정 사항

구현 전에 정해 둔다. 구현 중 바꾸려면 이 문서를 먼저 고친다.

| 항목 | 결정 |
|---|---|
| 체중 기반 상수 | 2-1의 표대로 확정한다: N=5, 반감기 2건, 3% / 1.0~4.0 kg, 최소 차이 1.0 kg, 폴백은 오차의 2배 이내 / 5.0 kg. 근거는 2-1에 있고 실데이터 검증은 없다. 옵션으로 노출하는 것은 허용 오차 비율 하나뿐이다. 실사용 데이터가 쌓이면 다음 버전에서 조정한다 |
| 비슷한 체중의 가족 | 오배정을 줄이는 장치는 이벤트뿐이다. `person` 연동은 하지 않는다. 같이 사는 사람이 함께 집에 있으면 존재 여부로 후보를 줄일 수 없고, 폴링으로 나중에 읽는 구조라 읽는 시점의 존재 상태가 측정 시점과도 맞지 않는다 |
| 지문이 불안정한 경우 | 시각이 `None`이면 지문은 값만으로 만든다. 같은 값이 연속되면 새 기록으로 보지 않는다(문서에 한계로 적는다). 규칙 기반은 시각이 없으면 `no_time`으로 미배정한다 |
| 폴링 사이 누락 | 최신 1건 모드의 누락은 허용된 한계다. 완화책을 만들지 않고 문서에 적는다. 이슈 작성자의 사용 패턴 확인은 출시 조건이 아니다 |
| 저장 기록 동기화 옵션 | 멀티유저와 엮지 않는다. 기존 옵션 `sync_stored_records`가 켜져 있으면 누적된 기록을 배정하고, 꺼져 있거나 옵션이 없는 기기는 최신 1건만 배정한다. 사용자 등록이 이 옵션을 바꾸지 않는다 |
| 서브엔트리 API | 필요한 서브엔트리 API와 테스트 헬퍼를 지원하는 최소 HA 버전과 최소 핀으로 올린다(`hacs.json`의 `homeassistant`, `requirements_test_min.txt`). 옵션 흐름으로 대체하지 않는다. 구현 순서 0번에서 필요한 버전을 정한다 |
| 동기화 켜짐 경로의 실기기 검증 | 확보 못 해도 출시를 막지 않는다. 자동 테스트로 검증하고 베타에서 "실기기 미검증"으로 명시한다. 정식 릴리스 전에 최소 한 건의 실기기 확인이 있으면 문구를 바꾼다 |
| 사용자 삭제 | 서브엔트리를 지우면 그 사용자의 Store 항목도 지운다. 마지막 사용자를 지우면 지문과 마지막 순번도 지운다(다음 등록 때 다시 기준선부터). 그 사용자의 과거 기록은 HA 기록에 남는다 |
| 미배정 기록 | 어떤 사용자에게도 기록하지 않고 이벤트로만 알린다. 기기 센서에는 영향이 없다 |

## 구현 메모

구현 순서 0번 확인 결과와 계획에서 달라진 점이다.

- **서브엔트리 API (0번)**: HA 2025.12.0(플러그인 0.13.298)과 2026.10.4(0.13.375) 두 버전 모두에서 `ConfigSubentryFlow`, `async_get_supported_subentry_types`, `async_add_entities(..., config_subentry_id=...)`가 동작하고 전체 테스트가 통과한다. 서브엔트리 추가·수정·삭제는 모두 엔트리 `update_listener`를 부르므로 엔트리가 리로드된다(`async_update_and_abort`를 쓴다. `async_update_reload_and_abort`는 리스너가 있으면 `ValueError`를 낸다). 최소 핀과 `hacs.json`은 올리지 않았다.
- **`via_device`**: HA 2026.10은 `via_device`(식별자 쌍)를 폐기 예정으로 두고 `via_device_id`(레지스트리 ID)를 쓴다. 최소 버전 2025.12.0은 식별자 쌍만 안다. 그래서 `DeviceInfo`에 `via_device_id` 키가 있으면 그것을, 없으면 `via_device=(DOMAIN, entry_id)`를 쓴다. 후자가 동작하도록 사용자가 한 명 이상 있는 엔트리에서만 기기 본체에 `identifiers={(DOMAIN, entry_id)}`를 추가로 등록한다(사용자가 없으면 지금과 같다).
- **대상 기기**: `num_users == 1`이면서 체중계(`WEIGHT`) 또는 혈압계(`BLOOD_PRESSURE`)인 경우만 서브엔트리를 제공한다. 슬롯 1개 체성분계(HBF)는 비목표라 제외한다.
- **전략 변경 시 초기화 범위**: 최근 배정 체중만 지우고, 사용자 센서가 보여 주는 마지막 값과 기록 지문은 남긴다(지문을 지우면 다음 폴링에서 기준선을 다시 잡아 정상 배정이 사라진다). 비교는 Store에 함께 저장한 전략 이름으로 하므로 옵션 흐름은 Store를 만지지 않는다.
- **서브엔트리 삭제 정리**: 삭제 직후가 아니라 리로드 때 `async_setup_users`가 Store를 읽으며 없어진 사용자를 버리고, 사용자가 하나도 없으면 Store를 지운다.
- **BMI 키**: 체중계 서브엔트리의 선택 항목 `height_cm`(사용자별 키)이다. 규칙 방식의 체중계도 같은 항목을 가진다.
- **규칙 입력**: 시간대는 `HH:MM-HH:MM, ...` 쉼표 구분 텍스트 한 칸이고 저장 전에 파싱해 검증한다. 규칙 없음·시간대 겹침 경고는 확인 단계(`confirm_no_rules`, `confirm_overlap`)에서 제출하면 저장된다.
- **`no_time` 판정**: 시간 규칙을 확인할 수 없는 사용자가 하나라도 남아 있으면(값 규칙은 통과) 다른 사용자가 확실히 일치해도 `no_time`으로 미배정한다. 그 사용자도 일치할 수 있어 결과를 알 수 없기 때문이다.
- **동기화 모드의 기준선**: 지문이 없는 첫 폴링은 이벤트를 배정하지 않고 마지막 순번만 `next_seq`로 맞춘다.
- **훅 실패 격리**: 사용자 배정 중 예외는 로그만 남기고 폴링과 뒤따르는 저장 기록 동기화를 막지 않는다.
- **번역하지 않은 것**: 사용자 센서 속성(`assignment` 등)의 이름은 번역하지 않는다(기존 BMI 속성과 같다).
- **전략 변경 뒤의 기존 사용자**: 서브엔트리 데이터는 전략을 바꿔도 그대로다. 규칙 방식에서 등록한 사용자는 예상 체중이 없어 체중 기반에서 후보가 되지 못한다. 옵션 설명에 "바꾼 뒤 각 사용자를 편집"하라고 안내하고, 설정 시 예상 체중이 없는 사용자를 경고 로그로 알린다. 반대로 체중 방식에서 등록한 사용자는 규칙이 없어 모든 기록에 일치한다(계획의 "규칙 없는 사용자" 동작).
- **혈압계 사용자의 파생 지표와 플래그**: 기기 센서와 같은 함수를 쓴다. 산술은 `omron_ble/blood_pressure_metrics.py`의 순수 함수이고 `parser.py`와 사용자 센서가 함께 호출하므로 둘이 어긋날 수 없다(키, 단위, 반올림, 가드, 열거 값 동일). 사용자 센서는 저장된 마지막 값(`sys`/`dia`/`bpm`)에서 읽을 때마다 계산한다. 새 기록은 마지막 값을 통째로 바꾸므로 맥박 없는 측정은 맥박 기반 지표를 알 수 없음으로 만든다. 이진 플래그는 `irregular_pulse`, `body_movement`, `cuff_loose`, `improper_position`을 Store의 마지막 값에 함께 저장하고(옛 Store에는 뒤의 둘이 없어 알 수 없음으로 보인다), 커프 착용(`cuff_fit`)은 기기처럼 `cuff_loose` 그대로다(문제 클래스라 켜짐 = 커프가 느슨함). 플래그는 모델의 기록 파서가 채우는 것만 만든다(`record_parsers.recorded_pressure_flags`): 6401 계열(HEM-6401T, 6410T)은 불규칙 맥박과 신체 움직임만, 나머지 슬롯 1개 혈압계(HEM-7600T 포함)는 넷 다. 이벤트 `omron_unassigned_measurement`의 내용은 그대로다. 번역 이름은 기기 엔티티의 이름을 그대로 쓴다.
- **규칙 입력 폼 개선**: 시간대를 텍스트 한 칸 대신 시작·종료 `TimeSelector` 두 쌍(시간대 1·2)으로 입력받고, `rules`·`pressure` 단계에서 "언제 측정하나요?"(펼침)와 "평소 범위 (선택)"(접힘) 섹션(`homeassistant.data_entry_flow.section`)으로 묶는다(이름·키는 최상위). 저장 형태는 그대로다: 서브엔트리 `data`는 평평한 키이고 `time_windows`는 `parse_windows`가 읽는 같은 텍스트(분 단위, 초는 버림)라 `users.py`·`assignment.py`는 바뀌지 않았다(앞의 "규칙 입력" 항목은 이 항목으로 대체된다). 편집 시 저장된 텍스트로 선택기를 채우고, 베타(4.6.0-beta.1)에서 시간대가 둘보다 많이 저장된 사용자는 설명의 `{extra_windows}` 자리에 선택기에 보이지 않는 나머지 시간대와 "저장하면 보이는 둘만 남는다"는 안내를 보인다(번역은 `error.extra_windows_note`에서 읽는다). 규칙 없는 사용자가 이미 있는데 또 규칙 없이 저장하면 `confirm_no_rules_shared`로 "누구에게도 배정할 수 없음"을 경고한다(저장은 가능). 프런트엔드 화면은 확인하지 못했다.
- **시간대 목록 입력**: 시간대는 기본으로 하나만 보인다. `when` 섹션에 시작·종료 `TimeSelector`(`window_start`·`window_end`)를 두고, 그 아래 `more_windows`(`ObjectSelector`, `multiple: True`, 필드 `start`·`end`는 각각 필수 `TimeSelector`, `label_field: start`, `description_field: end`, `translation_key: time_window`)로 "추가" 버튼을 눌러 시간대를 개수 제한 없이 더한다(앞의 "시간대 1·2 선택기 두 쌍" 항목은 이 항목으로 대체된다). 저장은 기본 시간대 뒤에 추가한 시간대를 순서대로 이은 같은 텍스트(`06:00-08:00, 20:00-22:00`)라 서브엔트리 `data`와 배정 동작은 그대로다. 기본 시간대가 비어 있고 추가한 시간대만 있어도 된다. 오류는 모두 `when` 섹션 키에 붙는다(기본 시간대의 한쪽만 채움, 시작과 종료가 같음, 추가 항목의 시작/종료 누락 또는 해석 불가). 자정을 넘기는 시간대는 종료가 시작보다 이르면 된다. 편집 시 저장된 첫 시간대를 선택기에, 나머지를 `HH:MM:SS` 값의 `{start, end}` 목록으로 `more_windows`에 채우므로 4.6.0-beta.1·beta.2에서 시간대를 여러 개 저장한 사용자도 잃는 것 없이 열고 저장된다. 그래서 `{extra_windows}` 자리와 `error.extra_windows_note` 문구는 없앴다. 추가 항목 대화상자의 필드 이름은 `selector.time_window.fields.start.name`·`end.name`(모든 번역 파일)에서 읽는다. 프런트엔드 화면은 직접 확인하지 못했다(프런트엔드 소스로만 확인).
- **커프 비트의 뜻 (4.6.0-beta.2 수정의 정정)**: 기기 메모리 기록의 커프 비트는 커프를 제대로 감았을 때(커프 감기 OK 표시) 1이다. 처음 플래그를 넣은 #31은 이 뜻으로 `cuff_fit = not cuff`를 썼고, 나중에 붙은 이벤트 필드 이름 `cuff_loose = cuff`가 거꾸로였다. 4.6.0-beta.2는 그 이름을 믿고 기기 경로를 뒤집어 정상 착용이 "문제 있음"으로 보였다(실사용 보고로 확인). 이제 기기 센서는 `not cuff`, 이벤트의 `cuff_loose`는 `not cuff`, 사용자 센서는 `cuff_loose` 그대로라 세 곳 모두 켜짐(문제) = 헐거움이다. BLS 상태 비트는 규격대로 1 = 헐거움이라 그대로 둔다. 4.6.0-beta.2에서 Store에 저장된 사용자의 `cuff_loose`는 반대로 남아 다음 측정 때 바로잡힌다.
